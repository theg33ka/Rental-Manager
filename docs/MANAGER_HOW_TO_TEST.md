# How-to-test: виртуальный управляющий

## Подготовка

Для вопросов на чтение подходит обычная база. Сценарии с изменением оплат, сроков и отказом интеграций выполняйте в отдельном тестовом окружении: они меняют поведение напоминаний.

1. Обновите backend и web из этого checkout. Перед production migration нужен проверенный backup по [OPERATIONS_RUNBOOK.md](OPERATIONS_RUNBOOK.md). Alembic head — `20261002_01`. Новая таблица `agent_notifications` добавляется forward migration; старые финансовые таблицы не очищаются.
2. Войдите PIN владельца. Включите AI, supervisor и ежедневную сводку. Используйте существующий DeepSeek ключ. Настройки и вариант другого провайдера описаны в [MANAGER_AGENT.md](MANAGER_AGENT.md).
3. Откройте **Hermes → Виртуальный управляющий**. До первого LLM-запроса допустимо «ещё не проверен». После успешного вопроса должны появиться «работает», модель и время успеха.
4. Для телефона установите `android/RentalManager/build/rental-manager-mobile-0.1.13.apk`, войдите владельцем, разрешите системные уведомления и фоновые проверки. APK собран локально; публикация в канале автообновлений не выполнена этой задачей.

## 1. Текущий долг и источники — 5 минут

Выберите реальный договор и напишите:

> Какой сейчас полный долг по квартире [название], жилец [ФИО]? Проверь аренду, коммуналку и ручные долги отдельно.

Ожидается один итоговый ответ с разделом «Проверено». Сверьте суммы с карточками начислений. Частичный платёж должен уменьшать только свой канал; переплата ИП не должна погашать личную часть автоматически.

В **Hermes → Отладка** откройте запуск: должны быть реальные `query_records` и `get_debt_state`, аргументы, результаты и несколько LLM calls. Скрытых рассуждений модели в журнале нет.

## 2. История и сложный запрос — 5 минут

> Покажи долги по квартире [название] за весь период проживания [ФИО]. Отдели его договор от прежнего и следующего жильца.

> Кто за последние полгода чаще задерживал аренду больше чем на три дня? Покажи отдельно оплаченные задержки, текущую просрочку и случаи с неполной историей.

Ожидается поиск жильца, связанных договоров и начислений; для задержек — `analyze_payment_timing`. Если у двух людей одинаковая фамилия, агент должен уточнить личность. Старые зачёты без истории чеков должны оставаться неизвестными, а не считаться своевременными. При необходимости агент дочитывает страницы и длинные сообщения.

## 3. Решение по кейсу и память

1. Откройте нужный кейс. Напишите **«До понедельника не трогай»**.
2. Проверьте ответ, срок в «Обязательствах» и запись владельца в истории кейса. Время показывается по Новосибирску.
3. Обновите страницу или откройте Android → Управляющий → Чат → История разговора: переписка должна сохраниться.
4. До срока контроля по этому договору не должны уходить новые автоматические напоминания и одинаковые сообщения управляющего.
5. После наступления срока backend заново проверяет долг. Если он остался, ожидается сообщение со ссылкой на ваше решение. Если долг погашен в тестовой базе до срока, кейс и обязательство закрываются без напоминания.

Не нужно ждать реального понедельника ради автоматической проверки: unit-тесты ниже проверяют пятницу, понедельник и досрочную оплату с управляемыми датами.

## 4. Telegram и телефон

1. В «Каналы и время уведомлений» выберите один канал, включите проактивные сообщения. Для теста можно установить одинаковые начало/конец тихих часов: тишина будет отключена.
2. Используйте тестовый активный кейс с просрочкой 3–30 дней или назначенным контролем. Очень старый неизменившийся долг специально не создаёт новый alert.
3. Дождитесь фоновой проверки: worker стартует через 60 секунд после запуска приложения, затем работает раз в 15 минут. На телефоне также используется фоновый опрос, поэтому доставка не мгновенная.
4. В истории уведомлений Telegram должен перейти в **«отправлено»**, телефон — в **«показано на телефоне»** после публикации Android-уведомления. «Прочитано» не выставляется автоматически.
5. Повторите проверку без изменения кейса: нового одинакового уведомления быть не должно. В режиме «Оба канала» ожидается по одной записи на канал; в смешанном режиме критичные идут на телефон, остальные — в Telegram.
6. Ответьте через Reply на Telegram-уведомление: решение должно относиться к его кейсу. На Android откройте уведомление, затем «История и ответ» нужной ситуации.

Если Telegram показывает «отправка не подтверждена», сначала проверьте чат. Ручной повтор в web специально требует эту проверку, поскольку тайм-аут не доказывает, что сообщение не дошло.

## 5. Сводка и отсутствие спама

Выберите час ежедневной сводки, уже наступивший по Новосибирску, и дождитесь проверки worker. Ожидается одна сводка за день: полученные оплаты, сообщения жильцам и до трёх изменившихся ситуаций. Повторная проверка не создаёт вторую сводку. Старые неизменившиеся долги не должны заполнять её.

Фильтр кейсов по умолчанию — **«Требуют внимания сейчас»**. Переключение на **«Вся история»** должно показывать старые кейсы, сохраняя их финансовую историю.

## 6. Отказы и доступ

В тестовом окружении задайте недействительный ключ LLM и задайте вопрос. Ожидается честный отказ без выдуманных сумм, ошибка в статусе/журнале и системное уведомление при следующей проверке. Обычная бухгалтерия должна продолжать работать. Затем восстановите ключ и проверьте успешный вопрос.

Временно отключённый интернет телефона не должен превращать pending в delivered. После восстановления связи Android должен забрать очередь. Сценарии Telegram 429, тайм-аут и прерванная отправка дополнительно проверяются автоматически без реальных сообщений.

Под гостевым PIN чат, его история, настройки и подтверждения доставки недоступны. Изменяющие запросы без CSRF отклоняются.

## Автоматические команды

Из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_manager_agent tests.test_ai_providers tests.test_hermes_core tests.test_cash_migration -v
npm.cmd run check:js
powershell -ExecutionPolicy Bypass -File android/RentalManager/test-java.ps1
```

Backend-тесты создают собственные временные БД; LLM и Telegram подменены тестовыми transport. Миграционные тесты проверяют чистую и существующую SQLite схемы с контрольными данными.

Для полного browser-прогона используйте отдельную migrated test DB, синтетический owner PIN и переменную `PLAYWRIGHT_DATABASE_URL`; команды подготовки приведены в [TESTING.md](TESTING.md). Не направляйте browser suite на production: некоторые старые тесты создают тестовые платёжные профили.

```powershell
$env:PLAYWRIGHT_DATABASE_URL='sqlite:///data/manager-e2e-20261002.db'
npm.cmd run test:web
powershell -ExecutionPolicy Bypass -File android/RentalManager/test-ui.ps1 -Serial emulator-5554
```

Native UI smoke использует отдельный QA package без INTERNET и синтетические данные. Его успех проверяет интерфейс, но не заменяет пункты 1–6 с выбранным LLM и вашими интеграциями.

Известная проблема общего Python suite: прежний `test_month_progress_returns_only_current_salary_charge_for_replaced_tenant` ожидает `[3]`, получает `[8, 3, 2]`. Это воспроизведено на исходной финансовой функции; изменение управляющего его не исправляет.
