# Архитектурные решения

## Расходы жильца в счёт ИП-аренды — 18 сентября 2026

Расход с источником `rental_budget` и квартирой означает оплату жильцом нужд объекта в счёт аренды. Зачёт начинается с ИП-платежа за месяц расхода; превышение переходит в следующие ИП-платежи, личная часть не меняется. Жилец определяется по договору на дату расхода. Новый расход и зачёт сохраняются одной транзакцией. Для ранее внесённых расходов применяется явное идемпотентное действие «Зачесть в ИП»; массового пересчёта при запуске нет. Платежи зачёта связаны с исходным расходом через `source=expense_credit:<id>` и не создают зеркальных расходов.

## ADR-001: Backend является единственной границей бизнес-операций

Web, Android, Telegram и AI вызывают общие backend operations. Клиентская доступность кнопки не заменяет authorization, validation и транзакцию.

## ADR-002: Финансовые таблицы являются источником истины

Договоры, начисления, оплаты, коммунальные данные и расходы первичны. Hermes хранит производные cases/briefings/memory и reconciles их с бизнес-данными.

## ADR-003: Alembic-история forward-only

Опубликованные миграции не редактируются. Schema change, data repair и persisted access recovery выполняются новой линейной revision и проверяются на существующем upgrade path.

## ADR-004: LLM ограничен контекстом и safety registry

LLM классифицирует или формирует envelope, но не получает прямой доступ к БД и не определяет права. Backend повторно валидирует состояние; рискованные действия требуют proposal, а критические — повторного PIN.

## ADR-005: Один backend contract для web и Android

`/api/bootstrap`, `/api/app-state` и Hermes endpoints обслуживаются общим backend слоем. Нативный Android-клиент не является отдельной реализацией бизнес-правил.

## ADR-006: Production secrets находятся вне Git

Deployment secret store и persistent encryption-key file владеют runtime credentials. Репозиторий хранит только `.env.example`; production database exports, чеки, APK и signing keys не коммитятся.

## ADR-007: Реквизиты переиспользуются профилями и разрешаются по иерархии

`PaymentProfile` является глобальным справочником. Квартира использует собственный override, иначе default объекта, иначе legacy global settings. Архивный назначенный профиль не заменяется молча, но не может быть назначен новой связи. Используемый профиль не удаляется. Фактические реквизиты определяет один backend resolver для сообщений, tenant context и проверки чеков.

Смена профиля не переписывает сохранённые `PaymentReceipt`, документы и `MessageLog`. Snapshot профиля для уже созданного, но не оплаченного начисления пока не хранится; это открытое продуктовое решение в `PRODUCT_UI_CAPABILITY_MAP.md`.

## ADR-008: «Главная» и «Сегодня» решают разные операционные задачи

«Главная» остаётся постоянной точкой входа с общей сводкой портфеля, ближайшими решениями и быстрыми действиями. «Сегодня» остаётся отдельным постоянным разделом с полной приоритизированной очередью. Частичное дублирование допустимо, когда сокращает путь до действия. Новый web-интерфейс поддерживает белую и неоновую палитры с одинаковой структурой и доступностью; неоновая используется по умолчанию. Цвет не является единственным признаком статуса.

Новый ADR добавляется для решения с долгосрочными последствиями. Отмена старого решения оформляется следующей записью со ссылкой, а не тихим переписыванием истории.

## ADR-009: Коммуналка привязана к периоду проживания и объекту

Коммуналка рассчитывается по истории договоров, включая закрытые, внутри выбранного интервала показаний `[начало, конец)`. Дата окончания договора включительна; при переезде 08.09 старый договор заканчивается 07.09. Пустующие дни не начисляются следующему жильцу. Пересекающиеся договоры одной квартиры требуют исправления дат до расчёта.

Период каждой строки сохраняется в `metadata_json.line_period_start/line_period_end`; ранее созданные строки читаются совместимо из даты в примечании. Повторный расчёт исключает только фактически выставленные интервалы строк, кроме отменённых начислений и авансов. Web-черновик разделяет строки по квартире и договору. Предпросмотр выставления помечает ранее выставленные долги отдельно и ограничивает их выбранным объектом.

## ADR-010: Календарь показывает текущую оплату периодов проживания

Календарь является read-only проекцией договоров и финансовых строк в `services/payment_calendar.py`. GET не создаёт начисления и не изменяет статусы. Даты запроса включительны, интервалы строк в ответе полуоткрытые; исходный включительный период аренды передаётся отдельно. Цвет — текущая оплата счёта, покрывающего день, а не реконструкция состояния на прошлую дату. Суммы в деталях относятся ко всему указанному периоду, не делятся на дни и не суммируются между ячейками.

Авансы и черновики не означают оплату фактической коммуналки. При нескольких услугах непогашенный счёт имеет приоритет над оплаченным; отсутствие расчёта одной из активных услуг помечается отдельно. Новые и архивные объекты/квартиры берутся из БД. Режим аренды показывает сохранённые начисления договора, без предположения о переносе денег между договорами; агрегированный долг человека остаётся в существующем финансовом контуре.


## ADR-011: Бесконечная шкала и пропуски коммунальных начислений

Дополняет ADR-010. Все квартиры выводятся по высоте страницы. Горизонтальная шкала виртуализирует дни и подгружает окна по 120 дней; клиент хранит не более 8 окон. Масштаб 10–200% привязан к курсору, при отдалении подписи упрощаются. Полосы объединяют только соприкасающиеся сегменты одного счёта и договора; суммы сохраняются за весь период, без распределения по дням.

В коммуналке дни проживания без счёта за последние 31 день включительно нейтральные, более старые — жёлтые. Пропуск перед позднее полностью оплаченным периодом того же договора и услуги — красный. Оплаты другого жильца, отменённые счета, черновики и авансы не создают такой пропуск. Частично начисленные недавние дни сохраняют отдельную маркировку; просрочка счёта имеет приоритет. Финансовые строки остаются источником сумм, календарь их не изменяет.

Для переходов к скрытым красным дням backend возвращает сводку всей истории обходом границ договоров/счетов, без разворачивания каждого дня. И сводка, и окна используют одну функцию оценки дня. Это позволяет найти старую просрочку до загрузки её окна.
## Архив договоров, коммунальные суммы и история диалогов — 2026-09-18

- Поле `ignored` и прежняя отметка «Только для информации» означают «Архив»: сообщения и новые автоматические начисления отключены, существующие начисления, оплаты и долги сохраняются в календаре, сводках и отчётах. Долг жильца объединяет все его договоры, включая архивные; новый договор при переезде не наследует архивный статус. Архивирование не заменяет оформление даты выезда.
- Новые расчёты коммунальных услуг округляют сумму каждой строки жильца вверх до 10 рублей. Стоимость поставщика и уже сохранённые счета не пересчитываются; зачёт аванса выполняется после округления начисления.
- Отправленные Telegram-автоответы записываются в `MessageLog`. Диалог объединяет сообщения всех договоров жильца и по умолчанию возвращает всю сохранённую историю; повторное представление того же ответа в AI-журнале исключается. Ранее не сохранённые Telegram-автоответы задним числом не восстанавливаются.
## Android-обновления — 2026-09-19

APK хранится в GitHub Releases вне Git. JSON канала содержит версию и хеш именно собранного APK; серверный endpoint извлекает метаданные из бинарного manifest. Клиент сначала обращается к настроенному серверу, при недоступном APK — к фиксированному публичному каналу этого репозитория. Скачанный пакет должен совпадать по package и сертификату с установленным приложением и иметь больший versionCode. Установка требует системного подтверждения Android; сессия панели не передаётся GitHub. Автоматическая загрузка разрешена через Wi-Fi и мобильную сеть, кроме роуминга. Фоновая проверка не зависит от настройки финансовых уведомлений.
