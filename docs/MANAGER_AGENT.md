# Виртуальный управляющий: результат работы 02.10.2026

## Аудит и проблема

Rental Manager использует FastAPI/SQLAlchemy, SQLite локально и PostgreSQL в deployment. `main.py` связывает финансовые операции, Telegram webhook, DeepSeek и фоновый reminder worker. Android — Java, доставка уведомлений через JobScheduler и опрос bootstrap, FCM нет.

Hermes уже имел события, кейсы, обязательства, память, proposals и аудит. Owner-вопрос получал заранее выбранный snapshot и один completion. Обязательство не гарантировало паузу tenant reminders, единой истории доставки owner-уведомлений не было. Финансовые таблицы и договоры остаются первичными.

## Что реализовано и какие файлы изменены

- `services/hermes/agent_core.py`: настоящий цикл native function calls и проверяемый `finish_answer`.
- `services/hermes/data_tools.py`: общий read-only каталог, постраничные запросы, debt state, backend-агрегаты.
- `services/hermes/notifications.py`, `models.py`: сохраняемая очередь, настройки каналов, дедупликация и сводка.
- `main.py`, `services/ai_providers.py`, `services/deepseek_client.py`: интеграция owner flow, provider abstraction, web API, worker и учёт каждого вызова.
- `services/hermes/memory.py`, `cases.py`, `reminders.py`, `control_center.py`: паузы, решения и история кейсов.
- `migrations/versions/20261002_01_agent_notifications.py`: добавочная forward migration без удаления финансовых данных.
- `static/app.js`, `static/index.html`: чат, состояние AI, настройки, история уведомлений и кейсов.
- Android `DashboardDigest`, `NotificationRepository`, `NotificationHelper`, manifest: получение очереди и подтверждение показа; версия 0.1.13/code 14.
- `tests/test_manager_agent.py`, `test_cash_migration.py`, `tests/e2e/manager.spec.js`, `playwright.config.js`: проверки и выбор отдельной web test DB.

## Как работает агент и доступ к данным

Owner Telegram и web `/api/hermes/chat` вызывают общий `call_agent_envelope` → `run_agent`. Модель сама выбирает tools, читает результаты, делает дополнительные запросы и возвращает один ответ. Старые общие команды «список должников» и «как там по должникам» сохраняют детерминированный ответ. Tenant flow и подтверждения операций сохранены; новый web chat поддерживает чтение и решения по кейсам.

Tools: `catalog`, `query_records`, `get_debt_state`, `aggregate_records`. Доступны объекты, квартиры, жильцы, договоры/периоды, начисления, оплаты, коммуналка, счётчики, авансы, ручные долги, расходы, сообщения, события, кейсы, обязательства, автоматизации и runs. Фильтры равенства, gte/lte/in и страницы after_id позволяют читать историю за нужный период. Агрегаты count/sum/group считает backend. События показывают только разрешённые поля snapshot.

Текущий долг по одному договору рассчитывают существующие backend-функции: аренда, коммуналка и ручные долги. Чеки не вычитаются повторно из оплаченных сумм. Исторический долг на прошлую дату нельзя надёжно восстановить, если старые события отсутствуют.

Лимиты: 16 шагов, 60 tools, 180 секунд, 100000 символов контекста; страница до 100 строк/24000 символов; агрегат до 10000 строк/100 групп. Повтор одинакового вызова более двух раз останавливает цикл. Бюджет проверяется перед каждым completion. Ответ перечисляет реальные источники, отмечает недочитанные страницы и ошибки. Суммы с обозначением рублей должны присутствовать в evidence; это дополнительный барьер, а не доказательство всех смысловых утверждений модели.

## Память кейсов

«До понедельника не трогай» сохраняет сообщение, OwnerCommitment и suppression. Reconciliation сохраняет паузу; tenant reminders учитывают её. Досрочная оплата закрывает кейс и обязательство. В срок контроля агент снова проверяет кейс и напоминает о решении. Telegram reply привязывается к исходному уведомлению через message ID. В панели сначала откройте карточку кейса, затем напишите решение; при неоднозначности требуется выбор кейса. Срок хранится в UTC, отображается по Новосибирску.

## Уведомления, сводка и наблюдаемость

`agent_notifications` хранит очередь и статусы pending/sending/sent/delivered/uncertain/cancelled. Telegram подтверждает отправку, Android — публикацию уведомления; прочтение не предполагается. Неоднозначная ошибка Telegram переводит запись в uncertain без слепого повтора. Нужно проверить Telegram перед ручным повтором.

Режимы: Telegram, телефон, оба, критичные на телефон/остальные Telegram. Настраиваются тихие часы, время сводки, тон; пороги централизованы в NotificationConfig. По умолчанию внимание с 3 дней, критичность с 10 дней/100000 ₽. Долги старше 30 дней не создают новую очередь без назначенного контроля. Повтор зависит от суммы, уровня и срока контроля, а не ежедневного роста возраста долга. Архивные договоры исключены из новой проактивной очереди.

Сводка считает принятые оплаты и сообщения за местные сутки, включает до трёх изменившихся ситуаций. LLM формулирует факты; при недоступности остаётся backend-шаблон. Включённая новая система заменяет старую scheduled-сводку, чтобы не дублировать её. Время новой сводки по умолчанию 19:00, задаётся в Hermes. AI/supervisor/briefing выключатели сохраняются.

Журнал runs сохраняет tools/results, длительность, итог, stop reason, число LLM calls. Каждый запрос учитывается в usage; скрытые рассуждения не сохраняются. UI показывает provider/model, последний успех/ошибку, ошибки за сутки, конфигурацию Telegram и запуск worker. worker_started означает запуск потока, не доказательство его текущей исправности.

## Безопасность

Модель не получает SQL, произвольные таблицы, credentials или команды записи. Проекции полей заданы явно. Новые routes защищены owner middleware/CSRF. Финансовые записи и сообщения жильцам по-прежнему проходят backend validation, Action Safety Registry и proposal/PIN. HTTP-ошибки LLM не сохраняют сырое тело ответа. Финансовая логика работает без LLM.

## Проверки

- 24 новых unit/integration теста прошли: история, однофамильцы, частичная оплата/переплата, коммуналка, ручной долг, закрытый долг, 5+ tools, отказ необоснованной суммы, пауза/возврат/досрочная оплата, архив, сбои и дедупликация. Реальный путь web handler → core → mocked native transport проверен с учётом каждого запроса.
- 23 существующих Hermes/provider теста прошли; routing и migration проверки выполнены отдельно.
- Чистая и существующая SQLite схемы upgraded, контрольные записи/FK сохранены. PostgreSQL не проверялся.
- 21 прежний browser-сценарий прошёл на новой migrated test DB. Новый сценарий управляющего прошёл отдельно после исправления видимости карточки; desktop/mobile screenshots сохранены.
- Java: 32 assertions. APK 0.1.13 собран, подпись проверена apksigner. Эмулятор и телефон не подключены.
- Compileall, JS syntax, secret scan и targeted Ruff прошли. Общие Ruff/mypy имеют ошибки в прежнем коде; новые модули проверяются отдельно.
- Полный Python прогон выявил старое падение `test_month_progress_returns_only_current_salary_charge_for_replaced_tenant`: ожидается `[3]`, приходит `[8, 3, 2]`. Оно воспроизведено с исходной функцией из HEAD до изменения AI. Этот тест и финансовая функция не менялись.

## Что настроить вручную и как проверить

1. **Deployment:** сделать проверенный backup БД по OPERATIONS_RUNBOOK. В окружении приложения выполнить `python -m alembic upgrade head` (production startup уже это делает), перезапустить backend. Проверить head `20261002_01`, `/healthz` и Hermes. Production migration здесь не запускалась.
2. **LLM:** существующий DeepSeek ключ можно оставить; задать `AI_ENABLED=1`, сохранить DEEPSEEK_API_KEY/MODEL в окружении хостинга или защищённых настройках. Для другого OpenAI-compatible API получить ключ и model ID у провайдера, задать RENTAL_AI_PROVIDER=compatible, HTTPS RENTAL_AI_BASE_URL, RENTAL_AI_API_KEY, RENTAL_AI_MODEL. Перезапустить backend. Проверить свободный вопрос и tools в журнале. Прямой Anthropic Messages API не поддерживается.
3. **Telegram:** существующие бот, owner chat и webhook сохраняются. Если их нет: BotFather → токен в защищённое поле Telegram, ID владельца в TELEGRAM_OWNER_CHAT_ID; webhook по DEPLOYMENT.md. После перезапуска проверить /help и owner-вопрос. Ключи не помещать в Git.
4. **Расписание:** включить AI_SUPERVISOR_ENABLED=1; отдельный cron не нужен, используется reminder worker. В Hermes выбрать канал, тихие часы и час сводки; проверить queue и sent/delivered отдельно.
5. **Телефон:** установить локальный APK 0.1.13 с прежней подписью, войти owner PIN, разрешить уведомления и фоновые проверки. Firebase не требуется. Это опрос, не мгновенный FCM push. GitHub Release/update feed не публиковались; старый установленный APK новый канал не читает.
6. **Проверка сценариев:** спросить долг конкретного договора и сравнить источники с начислениями; спросить историю жильца с несколькими договорами; открыть кейс и отложить до понедельника; в тестовой базе погасить долг раньше срока; проверить закрытие, ответ на Telegram уведомление, daily summary и Android delivered. При отключении LLM в тестовом окружении расчёты должны продолжить работу.

## Что осталось

Не реализованы настоящий FCM push, прямой Anthropic adapter, универсальное восстановление старых финансовых состояний при отсутствии событий, тарифный adapter для стоимости сторонних моделей, полноценный native Android chat и distributed scheduler lease. Проактивность использует snapshot кейса, не полный многопроходный разбор каждого события. Реальные LLM/Telegram/телефон и PostgreSQL требуют отдельного smoke. Все критерии большого исходного задания полностью не закрыты; это рабочий фундамент с обозначенными ограничениями.
