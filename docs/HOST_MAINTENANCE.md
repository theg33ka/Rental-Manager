# Диагностика и исправления на хосте

Консольный клиент обращается к работающему приложению по HTTPS. Авторизация — существующий PIN владельца, обычная отзывная сессия и CSRF. Отдельных постоянных API-ключей, публичного SQL, shell и обхода authorization нет. После каждого запуска клиент отзывает свою сессию.

## Однократное подключение Windows

После deployment текущего кода владелец выполняет из корня проекта:

```powershell
.\scripts\maintenance\host.ps1 -Configure -Url https://ваш-хост
```

PIN вводится в локальном скрытом приглашении, не в чате и не в аргументах команды. Windows DPAPI сохраняет его для текущего Windows-пользователя в `%LOCALAPPDATA%\RentalManager\maintenance\owner.xml`; origin находится рядом в `host.json`. Эти файлы находятся вне репозитория. Доступ имеют процессы этого пользователя Windows, включая агента, запущенного от его имени. Настройка сохраняет уже существующий доступ владельца, не создаёт новый серверный аккаунт и не меняет PIN. Для смены хоста повторите `-Configure`; обычный запуск не принимает другой URL. Отзыв локального доступа: удалите эти два файла. Если нужно отозвать сам PIN, используйте штатную смену доступа владельца.

Альтернатива для других ОС: `host_client.py --url https://ваш-хост ...` с PIN в переменной процесса `RENTAL_MAINTENANCE_PIN`. Не передавайте PIN в command line и не печатайте окружение. `RENTAL_MAINTENANCE_URL` может задавать origin. Для синтетического локального теста разрешён HTTP на localhost.

## Чтение

```powershell
.\scripts\maintenance\host.ps1 -Command inspect -ApartmentId 3
.\scripts\maintenance\host.ps1 -Command proposals
```

`GET /api/admin/maintenance/apartments/{id}?limit=100` отдаёт финансовые записи только выбранной квартиры: договоры, аренду, коммунальные строки и родительские счета, оплаты, журнал авансов и ручную настройку прогноза. Значения отражают сохранённое состояние, без генерации начислений и пересчёта статусов. В каждой коллекции максимум 500 записей, новые идут первыми; `truncated=true` означает неполную историю. Нельзя вычислять полный остаток по усечённому журналу. Реквизиты получателей, файлы чеков, контакты, PIN и integration settings не выдаются. Ответ не кешируется.

Вывод содержит реальные финансовые данные. Не коммитьте его, не передавайте другим агентам и не сохраняйте database export в материалы задачи.

## Исправление

Разрешены `update_payment_receipt`, `update_lease`, `update_apartment`, `repair_transfer_finance` из общего каталога owner operations. Для остальных исправлений сначала добавляется конкретная backend operation с regression test; произвольного изменения таблиц нет. Команды массового удаления, рассылки, импорта и восстановления через этот клиент не предлагаются.

`repair_transfer_finance` — явная runtime-сверка переезда: `source_lease_id`, `target_lease_id`, `expense_id`, `funding_apartment_id`, `duplicate_pairs` (пары `[original_id, duplicate_id]`, допустим пустой список). Нельзя выводить пары из одного совпадения сумм: сначала владелец подтверждает факт повтора. Источник бюджета фиксируется как происхождение расхода, без нового платежа от жильца квартиры-источника. Клиент не исправляет отложенную сверку наличных этой квартиры.

При `propose` backend рассчитывает изменения в savepoint и откатывает их, добавляет результат в preview и сохраняет fingerprint исходных договоров, оплат, счетов, журнала и расхода. Подтверждение уровня 3 требует PIN и неизменившийся fingerprint. Операция сохраняет отменённый зачёт и повторные оплаты, обнуляет ложное будущее начисление закрытого договора, восстанавливает журнал подтверждённого аванса, создаёт парный перенос, покрывает фактические выставленные счета только нового договора и уменьшает уже покрытую существующим остатком заявку на аванс. Перенос не создаёт PaymentReceipt. Повторное применение защищено аудитом. При изменении связей, сумм, исходных данных или несохранении денег транзакция откатывается.

Это отдельная согласованная runtime operation, а не автоматический repair при deployment; Alembic head не меняется. До подтверждения обязательны проверенный backup и показ конкретного preview. После применения проверяются обе квартиры; исходные чеки, расход и оплаченный период сохраняются.

1. Прочитайте данные и согласуйте точный scope исправления. Для persisted repair следуйте `CHANGE_AND_MIGRATION_GUIDE.md`; наличие клиента не отменяет forward migration там, где она требуется. Backup проверяется отдельно до production write.
2. Создайте локальный JSON-план в игнорируемом `data/`:

```json
{
  "operation": "update_apartment",
  "arguments": {"apartment_id": 3, "name": "БД3"},
  "reason": "Исправление подтверждённой ошибки в названии квартиры"
}
```

3. Подготовьте предложение:

```powershell
.\scripts\maintenance\host.ps1 -Command propose -PlanFile data\repair-plan.json
```

`POST /api/admin/maintenance/proposals` валидирует аргументы общей операцией, классифицирует Action Safety Registry, создаёт pending proposal с preview, TTL и ключом идемпотентности и сохраняет причину в `AiActionLog`. Финансовые данные на этом шаге не меняются. Telegram и LLM не вызываются.

4. Покажите владельцу preview и конкретные изменения. После его команды на применение:

```powershell
.\scripts\maintenance\host.ps1 -Command confirm -ProposalId 123 -Apply
```

Подтверждение идёт через существующий `/api/hermes/proposals/{id}/confirm`: backend повторно проверяет операцию, TTL, статус и требуемый PIN, выполняет общую operation и записывает аудит. Уже выполненное предложение повторно не применяется. Клиент подтверждает только proposals с `requested_by=maintenance`. При изменении исходных данных заново прочитайте их и подготовьте актуальное предложение: preview не блокирует записи от параллельного редактирования.

5. Повторите `inspect` и сверьте результат. Успешный HTTP-ответ или push сам по себе не подтверждает правильность финансового результата.

## Включение на Amvera

Сначала deploy backend и web, затем однократная локальная настройка доступа, owner-only read smoke и проверка запрета гостевого доступа. Исправление конкретных авансов выполняется отдельным согласованным шагом после чтения реальных записей. Схема БД и Alembic head для этого инструмента не меняются.
